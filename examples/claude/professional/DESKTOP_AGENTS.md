# 전문 데스크톱 프로젝트

- 먼저 제품의 핵심 흐름·대상 OS·파일/데이터 규모·GPU/지연·정밀도·오프라인·기존 코드와 라이선스를 확인한다. 기존 합의를 우선하고 결과를 바꾸는 미결정만 묻는다.
- 사용자 지정이 없으면 요구에 맞춰 C++/Qt, C#/Avalonia/WPF/WinUI 등 실제 지원 스택을 비교하고 선택 이유를 기존 설계 정본에 짧게 기록한다. 항상 한 프레임워크를 강제하지 않는다. 웹 요청이 없는 편집기·CAD·모니터링 프로그램을 HTML/Canvas/Three.js/브라우저 데모로 대체하지 않는다. 웹 기반 UI를 명시하지 않았으면 Electron/Tauri/WebView로 감싼 주 UI도 선택하지 않는다. 설치형 확장자만으로 네이티브 구현을 판단하지 않는다. 필요한 보조 웹 서비스는 제품과 구분한다.
- 문서/명령/undo·redo·선택/도구·UI·렌더링/작업 스레드·파일 입출력의 실제 소유 경계를 요구에 맞춰 둔다. 불필요한 플러그인 프레임워크나 병렬 상태 모델을 만들지 않는다.
- 큰 문서·저장 중 실패·중단·정밀도·메모리·취소·반응성·파일 버전 호환성을 대표 데이터로 확인한다. UI 스레드에서 긴 작업을 수행하지 않고 실제 병목으로 타일/스트리밍/캐시 등을 선택한다.
- 메인 에이전트가 구현·통합을 소유한다. 필요할 때만 설계 관점은 인터페이스/의존성/변환을, 그래픽 관점은 렌더/에셋/메모리를, 품질 관점은 실제 빌드·회귀·패키징을 검토한다. 작은 수정에 별도 에이전트 호출이나 새 보고서를 강제하지 않는다.
- 현재 버전의 빌드·테스트·실행 경로와 대표 기능을 실제로 연결해 확인한다. 가짜 화면·항상 성공하는 반환·출력 코드만으로 완료하지 않는다. 결과는 기능 구현·임시 리소스·시각 품질·성능·배포 검증을 구분한다.
