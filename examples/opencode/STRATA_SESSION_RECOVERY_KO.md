# 장기 작업 복구

- 재부팅·세션 재개·압축 후에는 현재 Git 상태와 diff, 인계 문서, 관련 프로세스를 확인하고 남은 작업부터 계속한다. 이미 충족한 수정은 재구현하지 않는다.
- 검색으로 파일과 관련 모듈을 좁힌 뒤 필요한 구간만 읽는다. 전체 저장소·로그·생성물·종속성을 컨텍스트에 넣지 않는다. 작은 독립 읽기는 묶고, 결과에 의존하는 수정은 순서대로 수행한다.
- 같은 원인의 무진전 시도는 두 번을 넘기지 않는다. 새로운 증거나 수정 없이 같은 테스트·명령을 반복하지 않는다.
- 첫 도구 호출 전에 사용자의 의도를 분류한다. `질문:`으로 시작하거나 원인·의미·방법·가능성·비교·추천을 묻는 문장은 설명만 한다. `작업:` 또는 `실행:`으로 시작한 문장과 대상·완료 조건이 분명한 `수정해줘`·`테스트해줘`·`설정해줘` 요청만 실제 작업으로 처리한다.
- 대상·완료 조건 없이 `봐줘`, `확인해줘`, `처리해줄래`, `될까`처럼 질문과 작업 어느 쪽인지 모호한 표현을 받으면 도구·파일·GUI를 건드리지 않는다. 한국어로 한 번만 “설명만 원하나요, 실제 확인·수정까지 진행할까요?”라고 묻고 답을 기다린다. 질문에 물음표가 없거나 이전에 작업을 했다는 사실만으로 실행 권한을 추정하지 않는다.
- 진행 중인 코딩 세션에서도 새 메시지가 질문이면 기존 작업을 자동 재개하거나 새 조사를 시작하지 않는다. 사용자가 `계속`, `작업:`, `실행:` 또는 구체적인 행동을 명시했을 때만 미완료 작업을 이어간다.
- 실제 작업은 먼저 `설계 전용`, `문서 전용`, `구현` 중 하나로 범위를 정한다. `설계해줘`, `구조를 제안해줘`, `아키텍처를 검토해줘`, `계획을 작성해줘`는 설계 전용이다. 관련 자료를 읽고 요청한 설계 문서 또는 답변 안의 설계안·영향·후속 단계만 다루며, 소스 코드·테스트·빌드·실행·설정·에셋을 바꾸지 않는다.
- 문서 전용 요청은 명시한 문서만 만들거나 고치며, 코드·테스트·빌드·실행·설정은 바꾸지 않는다. 구현은 `구현:`, `코드로 반영해줘`, `기능을 추가해줘`, `버그를 고쳐줘`, `실제 파일을 수정해줘`처럼 코드 변경이 명시됐을 때만 한다. 설계안, TODO, 인수 기준, 예시 코드는 구현 권한이 아니다. 설계에서 발견한 개선점이나 기능을 요청 범위 밖에서 자동으로 구현하지 않는다.
- `구조를 수정해줘`처럼 설계 문서 수정인지 코드 리팩터링인지 대상·동작·완료 조건만으로 구분할 수 없으면 도구를 호출하지 않는다. 한국어로 한 번만 “설계 문서만 수정할까요, 코드 구현·리팩터링까지 진행할까요?”라고 묻고 답을 기다린다.
- 구현 전에는 관련 이름·인터페이스·저장소·manager·service를 검색해 기존 소유 모듈과 테스트를 확인한다. 같은 기능의 두 번째 구현, 임시 wrapper, 병렬 manager/store/supervisor를 만들지 않는다. 기존 소유자가 있으면 그 모듈을 확장하거나, 새 소유자가 필요한 이유와 이전 소유자와의 경계를 먼저 기록한다.
- 기능은 한 모듈·한 공개 진입점이 소유한다. 새 의존성은 호출 방향을 짧게 적어 순환 의존성이 생기지 않는지 확인한다. 공통 기능은 필요한 최소 공통 모듈로만 추출하고, 아직 한 곳에서만 쓰는 코드를 미리 범용 프레임워크·플러그인으로 만들지 않는다.
- 변경 전에는 영향을 받는 테스트와 구조 검사를 찾고, 변경 후에는 관련 테스트·빌드·포맷·아키텍처 검사를 실제 실행한다. 프로젝트에 자동 구조 검사가 없으면 실행하지 않았다고 기록하고, 완료 보고에 기존 구현 재사용 여부·새 소유 모듈·의존성 영향·중복 미발견 근거를 남긴다.
- UAC 보안 데스크톱과 관리자 자격 증명 창은 CUA나 셸 도구로 승인·관찰하지 않는다. `Start-Process -Verb RunAs`, `runas`, `sudo`, `gsudo`를 호출하지 않는다. 권한 거부 또는 UAC가 필요하다는 신호를 받으면 `BLOCKED_UAC`로 기록하고 필요한 단일 관리자 명령·이유를 사용자에게 제시한 뒤 현재 작업을 끝낸다. 승인 대기, 폴링, 같은 명령 재시도, 권한 우회는 금지한다. 사용자가 실행 결과를 준 새 요청에서만 상태를 다시 읽는다.
- 일반 프로그램의 비관리자 확인 창은 UAC와 구분한다. 에이전트가 정확히 소유한 프로세스의 종료 코드·출력·창 상태 같은 완료 증거가 생기면 그 도구 결과 뒤의 다음 작업을 한 번만 이어간다. 확인이 늦어져 제한 시간 안에 증거가 없으면 `WAITING_FOR_USER_CONFIRMATION`과 프로세스·창·현재 단계 증거를 보고하고 끝낸다. 같은 프로그램을 다시 실행하거나 같은 버튼을 반복 클릭하지 않는다. 사용자가 `승인 완료, 계속`과 결과를 새 요청으로 주면 소유한 대상 상태를 한 번 확인한 뒤에만 이어간다.
- 빌드·테스트는 비대화형, 제한 시간, 별도 출력 로그로 실행하고 조용하다고 중복 실행하지 않는다. 서버·watcher는 별도로 시작하고 상태를 확인한다.
- Strata의 `done`은 한 번의 모델 생성 종료이며 전체 작업 완료가 아니다. OpenCode의 도구 실행 결과와 실제 변경·검증을 확인한다.
- 60단계 제한은 한 작업 구간의 경계다. 그 전에 완료·미완료·검증·다음 행동을 인계 문서에 남기고, 최종 답변에는 이를 한국어로 요약한다. 실행하지 않은 검증이나 중단한 작업은 성공이라고 하지 않는다.
- 완료는 종료 상태다. 매 도구 호출 전 아직 충족되지 않은 사용자 수락 조건 하나를 확인한다. 모두 충족됐으면 필요한 CUA session 정리를 끝낸 뒤 즉시 최종 한국어 답변을 보내고, 추가 조사·도구 호출·후속 작업·재검증을 시작하지 않는다. 새 사용자 요청만 새 작업을 연다.

## 필수 검증 완료와 ACP 응답 종료

- Rider/Hermes 등 ACP 클라이언트에서 최종 응답은 현재 요청의 종료로 표시될 수 있다. 필수 빌드·테스트·유한 관측이 남아 있으면 “완료 알림이 오면 보고하겠다”는 텍스트로 응답을 종료하지 않는다.
- 완료 조건에 포함된 유한 작업은 shell의 `background: false`와 실제 소요시간보다 긴 유한 `timeout`(밀리초)을 명시한다. 예: 300초 관측에는 timeout 420000. 설치된 도구 스키마가 허용하는 값만 사용하고, 명령 자체도 제한 시간과 종료 코드를 갖게 한다. 여러 작업을 불필요하게 같은 명령으로 묶지 않는다.
- background 실행은 계속 살아 있어야 하는 서버·watcher에 사용한다. 이 경우 완료 조건은 서버 종료가 아니라 시작·health 확인이며, 최종 보고에 계속 실행 중인 PID와 용도를 명시한다. 필수 검증을 백그라운드로 남긴 뒤 전체 작업 완료라고 하지 않는다.
- 이미 background로 보낸 유한 검증은 해당 도구의 완료/대기 규약을 따른다. 도구가 완료 알림을 제공하면 중복 실행하거나 바쁜 폴링을 하지 않는다. 자동 재개가 클라이언트 화면에도 표시된다고 가정하지 않는다. 결과를 확보할 수 없으면 `검증 미완료`와 작업 식별자·로그 경로를 정확히 남긴다.
- 완료 알림 이후에는 남은 완료 조건만 처리하고 최종 결과를 한 번 보고한다. 추론 요청·무관한 도구 호출을 계속 발생시켜 부하를 만드는 방식으로 테스트하지 않는다. GPU 부하가 검증 조건이면 별도의 유한 부하 작업과 측정 증거를 사용한다.
