# Claude Code 파일 읽기·쓰기 점검

2026-10-27, 현재 PC의 Claude Desktop Code → OpenCodex 10100 → Strata 8080 구성을 점검했다. 시험 범위에서는 파일 도구 실행보다 큰 읽기 결과를 모델이 처리하는 비용이 컸다. 기존 Claude 전용 지침 두 구간을 수정하고 새 네이티브 세션에서 실제 동작을 확인했다.

## 적용한 개선

- 알려진 작은 파일은 직접 Read한다. 큰 파일·긴 로그의 국소 작업은 필요한 함수·타입과 앞뒤 문맥을 offset/limit으로 읽는다. 위치를 모르면 해당 파일·모듈에 한정해 Grep하고 필요한 범위를 넓힌다. 한도 오류를 피하려고 전체 읽기 허용을 상시 사용하지 않는다.
- 기존 파일의 국소 수정에 전체 내용을 다시 생성하지 않는다. 작은 새 파일을 여러 Write·셸 append로 잘게 나누지 않는다. 출력 한도에 가까운 큰 구현만 일관된 변경 묶음으로 나누며, 잘림·불확실한 저장 뒤에는 실제 저장 상태를 확인한다.

`tools/claude_code_guidance.py`의 기존 실행 지침을 고쳐 새 설치용 원본에 반영했다. 현재 `~/.claude/CLAUDE.md`에는 동일한 관리 문구 두 곳이 정확히 한 번씩 존재하는 것을 확인한 뒤 그 부분만 병합했다. 사용자가 수정한 추론·병렬 실행·기타 지침은 보존했다. 전체 파일을 새 생성물로 덮어쓰거나 기존 사용자 수정 감지를 무효화하는 소유 해시 갱신을 하지 않았다. 백업·전후 SHA-256은 `guidance-publish.json`에 있다.

추가 MCP·상시 프로세스·매 도구 호출 훅·별도 파일 캐시는 만들지 않았다. 모델·컨텍스트·추론 기본값·권한·서버·디스크 설정도 변경하지 않았다. 새 Claude Code 세션에서 변경된 공통 지침을 불러와 검증했다. 기존에 열린 Desktop 대화의 지침 스냅샷 갱신은 별도로 측정하지 않았다.

Read의 범위 인자, 큰 파일 한도와 부분 결과, Edit의 현재 내용 일치·인코딩 처리는 [공식 도구 문서](https://code.claude.com/docs/en/tools-reference#read-tool-behavior)와 [Edit 설명](https://code.claude.com/docs/en/tools-reference#edit-tool-behavior)을 대조했다. 전체 분석이 필요한 요청까지 제한하거나 관련 호출부·계약을 버리는 고정 줄 수 상한은 추가하지 않았다.

## 최근 실제 네이티브 도구 기록

이전 재시작 진단 대화의 `tool_use` 기록 시각부터 같은 ID의 `tool_result` 시각까지 계산했다. Desktop 원래 턴과 같은 UUID의 임시 CLI 재개가 함께 포함된 네이티브 도구 표본이다. SDK가 재개하며 재기록한 동일 호출 ID는 중복 집계하지 않았다. 이 값에는 실행 대기·IPC·기록 비용이 포함되며 순수 디스크 시간이나 Desktop UI의 지연은 아니다.

| 도구 | 표본 | 중앙값 | 범위 |
|---|---:|---:|---:|
| Read | 4 | 41.5ms | 38–52ms |
| Write | 4 | 29.5ms | 22–44ms |
| Edit | 1 | 33ms | 33ms |
| Glob | 2 | 92.5ms | 89–96ms |
| PowerShell | 2 | 1,504.5ms | 1,491–1,518ms |

작은 진단 파일 표본이다. 모든 파일·프로젝트의 상한으로 해석하지 않는다. 바이트 검사가 필요한 PowerShell 호출도 포함되므로 이 두 호출을 불필요한 작업으로 삭제하지 않았다. 내용 조회·국소 편집만 필요할 때 기존 네이티브 도구를 우선할 근거로 사용했다.

## 로컬 파일 I/O

기존 `tools/benchmark_local_io.py`를 그대로 사용했다. OS 캐시는 유지했고 캐시 삭제·디스크 튜닝은 하지 않았다. 크기별 각 방식 5회, 총 45개 내용 검사가 통과했다.

| 파일 크기 | 전체 읽기 중앙값 | 1KiB 범위 읽기 중앙값 | 원자적 저장+fsync 중앙값 |
|---|---:|---:|---:|
| 8KiB | 0.091ms | 0.070ms | 1.089ms |
| 1MiB | 0.322ms | 0.071ms | 1.890ms |
| 16MiB | 4.427ms | 0.078ms | 12.261ms |

메모리에 캐시된 로컬 파일 시험이며 SSD의 cold 처리량·전원 장애 보장·동시 빌드 포화 상태 시험이 아니다. 이 결과만으로 백신·동기화·파일 저장 확인을 끄지 않았다.

## 같은 네이티브 실행 파일의 비교

Claude Desktop에 설치된 Claude Code 2.1.308을 기존 OpenCodex·Strata에 연결했다. 실행 파일 SHA-256은 `c9796ba22a9221586b36371b36f5b66198d66eb4badf6a4cf4a5f7b07becea53`이다. 시험 요청에만 Medium을 지정했고 운영 설정의 추론 성능은 바꾸지 않았다.

동일한 UTF-8 파일은 48,000바이트·806줄이며 대상 함수는 601행이다. 모든 경우 반환값 17을 18로 바꾸는 동일한 Edit 1회를 실행하고 외부 검사기가 다른 바이트까지 정확히 일치하는지 확인했다. 전체 Read 또는 지정 구간 Read를 명시한 방법 비교다. 지침 변경 자체의 보편적인 성능 향상률 시험으로 표현하지 않는다.

전체/범위 읽기 예열 1회씩은 제외하고 전체→범위→범위→전체 순서로 측정했다. 각 2회뿐이므로 통계적 보장으로 사용하지 않는다. 매 시작 전 현재 Strata 준비·슬롯 유휴를 확인했지만 다른 클라이언트의 미전달 대기열까지 독점 통제한 시험은 아니다.

| 방식 | 측정 총시간 | 중앙값 | Read 결과 길이 | 실제 도구 |
|---|---|---:|---:|---|
| 전체 읽기 | 17.7613초, 16.7594초 | 17.26035초 | 51,094자 | Read 1 + Edit 1 |
| 필요한 8줄 읽기 | 11.4440초, 10.6398초 | 11.0419초 | 360자 | Read 1 + Edit 1 |

이 격리 수정 시험의 중앙값은 약 **36.03% 감소**했고 Read 결과 길이는 약 99.30% 줄었다. CLI의 모델 API 누적 시간 중앙값도 14.959초에서 8.731초로 줄었다. 출력 토큰·캐시 적중 상태는 샘플마다 달랐으며 기록에 그대로 남겼다. 파일 도구 실행은 수십 ms인 반면 API 처리에는 초 단위 시간이 들어 읽기 결과의 분량을 줄이는 쪽이 효과적이었다. API 시간에는 모델 생성·추론·프록시·통신이 함께 포함되므로 순수 프리필 속도 향상이라고 단정하지 않는다.

총시간에는 네이티브 CLI 프로세스 시작과 훅 등이 포함된다. 상주 Desktop UI의 표시 지연을 포함한 완료 시간이나 모든 작업에서의 36% 향상으로 사용하지 않는다. 예열을 포함한 6회 모두 실제 파일 변경이 기대 바이트와 일치했다.

## 지침 적용 후 도구 선택·보존 확인

다음은 같은 네이티브 실행 파일의 새 세션에서 수행했다. 첫 시험에는 줄 번호나 읽기 범위를 주지 않았다.

| 요청 | 실제 동작 | 독립 결과 |
|---|---|---|
| 약 800줄 파일의 함수만 수정 | 해당 파일 Grep → Read(offset=590, limit=30) → Edit | 다른 바이트까지 일치, 15.5571초 |
| 한글 새 파일 저장 | Write 1회, 760자 | UTF-8·BOM 없음·LF·마지막 LF 하나 정확, 15.8553초 |
| 기존 한글·UTF-8 BOM·CRLF 파일의 값만 수정 | 작은 파일 Read → Edit | BOM·CRLF·한글과 나머지 바이트 모두 보존, 12.0479초 |

이 3건은 동작 확인이며 위 강제된 전체/범위 방법의 직접 시간 비교 표본에 합산하지 않았다. 완료 결과를 확인하려고 모델에게 같은 파일을 다시 읽게 하거나 별도 셸을 실행시키지 않았고 외부 검사기가 바이트를 확인했다. 실제 작업에서 바이트·인코딩 조건이 있거나 수정 결과가 불확실하면 필요한 검증은 계속 수행한다.

## 코드 검사·실패 기록·최종 상태


첫 진단 CLI 실행은 `--tools`를 마지막 옵션으로 배치한 상태에서 도구 실행 없이 2.8166초에 exit 1로 끝났다. 원래 결과와 초기 진단 스크립트를 보존했다. 옵션 순서를 고친 뒤 별도 진단 폴더에서 6회 방법 비교와 3회 적용 검증을 실행했다. 최초 오류 원문은 기록기가 보관하지 않았으므로 정확한 오류 문자열까지 확인한 것으로 보고하지 않는다. 실패를 원래 방법의 성능 측정에 포함하지 않았다.

진단 스크립트·원시 시간·도구 호출 메타데이터·파일 보존 결과는 `C:\Users\luiny\Strata-data\diagnostics\file-io-20261027`에 있다. `local-disk/results.json`, `native-run-v2/native-results.json`, `native-policy-verification.json`, `historical-desktop-tools.json`, `comparison-summary.json`, `guidance-publish.json`이 근거다. 모델의 내부 파일 도구나 설치된 Desktop 바이너리를 수정하지 않았다.

최종 읽기 전용 확인에서 `ready=true`, `desktop_ready=true`, Strata 슬롯 idle, RTX 3090 Ti, 서버 컨텍스트 262,144를 확인했다. 이 회차에는 서버·Desktop을 재시작하지 않았다. 262K 경계·자동 압축·대형 프로젝트·원격/네트워크 드라이브·다른 OS·I/O 포화 상태는 이번 시험에서 측정하지 않았다. 기존 미커밋 작업을 보존했고 커밋·푸시는 하지 않았다.
