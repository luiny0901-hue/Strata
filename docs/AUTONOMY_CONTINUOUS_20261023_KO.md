# 연속 세션·실패 처리 점검 — 2026-10-23

## 판정과 범위

**PARTIAL.** 이전 시나리오별 새 프로세스 검사와 달리, 이번에는 설치된 OpenCode 2.0.22의 **동일 프로세스·동일 ACP 세션**에서 서버 재시작 → 도구 결과 → 후속 생성 → 요청 종료를 50회 연속 수행했다. 두 번의 독립 실행에서 모두 통과했다. 서버는 실제 자식 프로세스를 교체하지만 모델 응답은 CPU 모의 서버가 정해진 도구 호출을 반환한다. 실제 모델의 코딩 판단·GPU 부하·Rider/Hermes UI·밤샘 안정성 증거가 아니다.

## 확인하고 수정한 부분

1. 상태 조회마다 16K 체크포인트를 JSON으로 변환하고 다시 읽어 복사했다. 상태 레코드의 값이 문자열·불리언인 점을 이용해 별도 딕셔너리 복사로 바꿨다. 반환값을 바꿔도 원본 상태는 바뀌지 않는 회귀 검사를 추가했다.
2. 재시작 완료를 저장하는 `save(ready)`와 작업별 결과 저장 사이에 스케줄링 간격을 주입했을 때, 결과 파일이 없는데 READY가 노출되는 것을 재현했다. 최종 결과와 현재 상태를 저장한 뒤에만 메모리 상태를 공개한다. 끝난 스레드가 잠시 살아 있다는 이유로 다음 요청을 거절하지 않도록 실제 트랜잭션 상태를 사용한다.
3. 결과 저장 실패는 READY가 되지 않고 추가 재시작을 차단한다. 작업 스레드를 시작하지 못한 경우도 계속 queued로 남기지 않고 실패로 기록한다.
4. 일반 OpenCode `Tool.Result`에는 MCP의 `isError` 필드가 없다. 재시작 도구가 실패 문구와 `isError: true`를 반환해도 일반 도구 완료로 보일 수 있었다. 실패는 예외로 전달하도록 수정했다. 설치된 ACP에서 `tool_call_update.status=failed`와 실패 결과를 받은 후속 모델 응답을 확인했다.
5. 백엔드 `/health`·`/v1/models`·`/slots` 응답은 최대 256KiB만 읽는다. 서버 수정 중 잘못된 큰 응답을 보내더라도 무제한으로 읽지 않으며 준비 미확인 오류로 처리한다.

## 회귀와 실패 이력

- Python 관련 회귀 55개 통과. 이 중 관리 경로 24개에 상태 복사·큰 응답·결과 저장 실패·스레드 시작 실패·조기 READY 검사가 포함된다.
- JavaScript 관련 34개 통과: 서버 관리 도구, 출력 복구, 실제 Node 프록시+가짜 CUA 드라이버의 오류/EOF 처리.
- `restart-failure-acp-20261023-a`: 준비 실패를 주입해 실제 ACP의 도구 실패 상태와 실패 결과 전달을 통과했다. 테스트의 초기 출력 문구는 준비 성공을 전제로 했지만, 실제 검사는 failed 상태를 요구했다. 이후 출력 문구도 성공/실패 모드에 맞게 고쳤다.
- `continuous-acp-20261023-final`: 최종 관리 코드·최종 플러그인으로 같은 세션 3회/모델 요청 6회 통과.
- 최초 READY 회귀 검사 초안은 상태 조회가 잠금 때문에 대기한 뒤 반환하는 경우를 고려하지 못해 실패했다. 검사 조건을 결과 파일 존재 여부로 바로잡고 `save(ready)` 이후의 실제 간격을 노출해, 수정 전 다시 실패를 확인했다. 수정 후 통과했다.
- 일반 도구 실패를 예외로 요구하는 Node 회귀 검사는 수정 전 `Missing expected rejection`으로 실패했고 수정 후 통과했다. 실패를 통과 이력으로 덮어쓰지 않는다.
- 50회 실행의 기존 요약 출력은 “두 모델 요청”이라고만 적었지만 각 턴마다 두 요청을 검사했고 최종 누계는 100이었다. 출력 문구를 총 턴/요청 수로 수정했다. 원본 JSON과 이벤트는 유지한다.

원본은 `~/Strata-data/diagnostics/`의 위 실행 폴더, `continuous-results.json`, `requests.json`, `events.json`, `stderr.log`에 있다. 매 실행은 새 폴더를 사용한다.
