# 긴 컨텍스트 처리 전략 비교 — 2026-10-23

## 결론과 적용

**128K 일괄 조기 압축은 적용하지 않았다.** 문맥이 잘 재사용되는 요청에서는 요약 비용이 추가돼 이번 사례의 다음 작업이 느려졌다. 기존 최대 262,144, 자동 압축 기준 196,608, 최근 기록 보존 12,000을 유지했다.

측정으로 확인한 전략을 기존 복구 지침에 반영했다. 변경 없는 코드/로그 반복 입력을 피하고, 요청 조립 코드를 다룰 때 실제 변경 없이 고정 지침·도구 정의를 재정렬하거나 앞부분에 매번 임시 상태를 넣지 않는다. 필요한 부분을 추릴 때 최신 변경·호출부·제약도 보존한다. 길다는 이유만으로 매 요청 수동 압축을 하지 않으며, 실제 진단 시 새 프리필과 재사용·요약·후속 작업 비용을 함께 비교한다. **지침 보완이며 자동적인 지연 단축을 보장하는 런타임 패치가 아니다.**

## 실제 Strata 조건

- 실행 중인 NVFP4 포크 + Unsloth UD-IQ4_XS, uncensored ON 서버를 재시작하지 않고 사용했다. 각 요청 전 `/slots` 유휴 상태를 확인했다. 오류 시 같은 요청을 자동 재시도하지 않는다.
- 검사 뒤 프로세스/명령·GPU 연결을 확인했다. 엔진 PID 28180은 GPU 1 RTX 3090 Ti에 연결돼 있었다. 모델·팩 경로와 엔진 해시는 `server-identity-after.json`에 보존했다. 모든 모델 파일을 다시 해시한 검사는 아니다.
- 실제 실행 인자는 `--max-context 262144 --kv int8 --kv-resident 32768 --expert-cache auto --spec 4 --vram-reserve-mib 448`이었다. 이전 문서/템플릿의 reserve와 다르므로 이전 측정과 동일 설정이라고 가정하지 않는다. 변경하지 않았다.
- 이 시험 요청에만 `reasoning_effort=none`, temperature 0, 출력 상한 384를 사용했다. 실제 출력은 25~42토큰이었다. 사용자가 선택한 OpenCode 추론 수준·출력 한도는 변경하지 않았다.
- 앞/중간/끝에 있는 계약 값 4개를 추출하는 합성 자료다. 대규모 코딩 정확성·긴 생성·실제 OpenCode 자동 요약 품질을 증명하지 않는다.

필요 기록만 입력한 경우 93토큰이었다. 이는 필요한 값의 위치를 아는 합성 사례로, 일반 프로젝트를 93토큰만으로 처리할 수 있다는 뜻이 아니다. 조건마다 출력 형식과 생성 토큰 수도 일부 달라 순수 입력 길이만의 효과로 해석하지 않는다.

요약 요청 자체도 기존 원문의 앞부분을 상당량 재사용했다. 245K 사례에서는 224,000토큰 재사용에도 21,611토큰을 새로 읽었다. 요약 후 답변 시간만 보고 원문 처리 비용이 없어진 것으로 계산하지 않았다. 반대로 향후 작업이 매우 많거나 문맥 재사용이 깨지면 요약의 누적 이득이 생길 수 있으나, 이번 단일 사례로 손익분기점이나 기본 압축 시점을 결정하지 않는다.
