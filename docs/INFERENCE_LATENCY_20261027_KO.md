## 깊게 생각하기: 추론량과 재개 비용을 분리

실제 프로필은 이미 Low 3,072 / Medium 4,096 / High 8,192의 선택별 한도를 적용하고 있었다. 실행 중인 다운로드 포크의 연결 코드는 운영 루트의 `tools/strata_anthropic_effort.py`와 `tools/patch_nvfp4_server_effort.py`가 소유한다. 다른 작업 트리의 server.py로 덮거나 같은 기능을 다시 구현하지 않았다. 해당 소유 모듈의 기존 CPU 계약 검사 6개도 통과했다.

초기 추론 시험의 요청에는 진단용 `reasoning_budget_tokens=8192`가 있었지만, 설치된 OpenCodex native Messages 전달부는 고정 허용 목록 밖의 이 필드를 제거한다. 따라서 Low·Medium의 실효 한도는 8,192가 아니라 위 프로필 값이다. 초기 결과 JSON의 budget은 요청값이며, 실효 한도와 전송 경로의 구분은 `thinking-request-controls.json`에 기록했다. 직접 API의 MTP·PCIe 시험에서는 명시한 8,192가 적용된다.

## 실패와 남은 한계

총 50개 모델 응답 중 48개가 독립 결과 검증을 통과했다. 예열도 이 개수에는 포함하고 성능 중앙값에서는 제외했다. 두 실패는 숨기지 않았다.

1. 초기 계획 시험의 두 번째 Low는 `core, render, metrics, mobile`을 선택해 비용 24라고 답했지만 E 기능이 빠졌다. 해당 행렬은 여기서 종료했다. 실패 행의 응답·시간은 남았고 당시 진단 코드가 정답 검사 뒤에 저장하던 일부 엔진/생각 통계는 없다. 이후 통계부터 검사보다 먼저 보존하도록 **진단 스크립트만** 고쳤다. 실패 요청을 재실행해 기록을 대체하지 않았다.
2. 후보 시험 후 오버라이드 없는 직접 High 요청은 `save_file` 호출 없이 `Saved calculator.py.`라고 답했다. save_file은 실제 실행되지 않았으며 코드가 저장됐다는 증거도 없다. 도구 누락으로 실패 처리하고 예정된 후속 프록시 요청을 보내지 않았다. 마지막 응답은 성능 정상 복귀의 관측이지 도구 작업 성공 증거가 아니다. 이 모델 응답 문제는 이번 성능 시험에서 해결하지 못했다.

이 실패 때문에 추론 한도를 더 줄이거나 속도만으로 설정을 채택하지 않았다. 정상 수신·SSE 종료·114.7 tok/s만으로 작업 성공을 보고하면 안 된다. 복잡한 프로젝트 전체의 무오류 동작이나 병목이 모두 사라졌다는 결과도 아니다.
