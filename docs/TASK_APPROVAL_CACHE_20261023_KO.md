# 초기 MCP 준비와 작업 단위 CUA 승인

## 적용한 동작

- ACP guard의 선택 옵션 `mcpStartupBarrierMs=15000`을 현재 PC에 적용했다. 첫 사용자 요청에서만 MCP 초기 연결이 성공/실패 등 확정 상태가 되고 도구 레지스트리가200ms 동안 안정될 때까지 기다린다. 실제 준비가 끝나면 즉시 진행하며15초를 고정 대기하지 않는다. 이후 요청은 같은 준비 결과를 재사용한다. 모델 예열 호출은 추가하지 않는다.
- 한도가 지나거나 MCP 조회에 문제가 있으면 무제한 대기하지 않고 진행한다. 아주 늦은 연결·재연결·실제 도구 변경은 이후에도 목록을 바꿀 수 있으므로 모든 캐시 손실을 제거하는 기능은 아니다.
- CUA 첫 전경 입력 때 `작업 완료까지 허용`을 한 번 선택하면 현재 ACP 요청의 후속 입력은 다시 묻지 않는다. 여러 정확한 앱 창을 사용할 수 있다. 요청 완료·실패·취소·연결 종료 시 해제하고 다음 요청·다른 채팅으로 이어지지 않는다. 거절/승인창 만료 뒤 같은 요청에서 계속 확인창을 띄우지 않는다.
- ACP 실행기가 실제 요청/응답으로 작업 키를 생성·종료하고, MCP 프록시는 OpenCode의 `ai.opencode/sessionID` 메타데이터와 대조한다. 모델 인자로 승인 상태를 생성·연장하지 않는다. 압축이나 모델 내부 여러 호출은 같은 활성 요청에 속한다. 하위 분석의 GUI 입력은 승인된 부모 요청에서 처리한다.
- 새 창 관찰, PID/창 ID·좌표 검증, 문자 전달 대기, UAC/보안 데스크톱 및 데스크톱 전체 입력 금지는 유지한다. 이미 전달된 입력은 취소로 되돌아가지 않을 수 있다.
- 작업 수명을 전달하는 실행기가 없는 일반 MCP 연결은 동작1회 승인이다. 현재 Rider ACP 엔트리2개를 새 실행기로 갱신했다. Windows/macOS 클라이언트 설치 원본에도 실행기·프록시 지원 코드를 포함한다. 초기 준비 대기는 선택 설정으로 현재 PC에 활성화했으며 설치기의 미선택 기본값은 유지한다.

## 실제 모델 비교

설치 OpenCode2.0.22 + 실제 Strata IQ4_XS High, 격리 DB/파일, 초기 tools/list가1200ms 늦어지는 모의 MCP를 사용했다. GUI 도구나 원본 프로젝트를 조작하지 않았다. 모의 도구는 실제 CUA와 같이 `codemode:false` 직접 호출 방식으로 노출했다. 초기 작업은 두 파일 읽기→합계42 저장→다시 읽기다. 같은 첫 요청을 비교했으며 CUA 승인 대기/입력 시간과 실제 Rider 렌더링 시간은 포함하지 않는다.

| 비교 | 준비 대기 없음 | 준비 후 시작 | 첫 작업 콜드 모델 호출 |
|---|---:|---:|---|
| direct-a | 17.774초 | 11.314초 | 2→1 |
| direct-b | 19.356초 | 9.352초 | 2→1 |

네 첫 작업의 파일·보고·종료 확인은 통과했다. 준비는 약1.50초에 끝났다. 표본은 각2개이며 저장소 위치와 캐시 상태가 완전히 같은 반복은 아니므로 모든 프로젝트의 속도 향상률로 일반화하지 않는다. 후속 작업에서는 초기 준비를 반복하지 않는다.

### 실패 및 검사 보정 기록

- 초기 a 쌍은 모의 MCP initialize에 protocolVersion이 빠져 연결에 실패했다. 파일 작업은 끝났지만 해당 쌍은 MCP 성능 비교에서 제외했다.
- b/c 초기 탐색은 Code Mode 및 read/edit/write 제한으로 실제 CUA의 직접 도구 스키마 추가 비용을 재현하지 못했다. 시간 이득이 일관되지 않아 그 결과만으로 활성화하지 않았다. 원본 결과를 보존했다.
- direct-a의 준비 대기 없는 후속 요청은 실제 파일이42인 채43으로 완료 보고해 검사가 실패했다. 이 결과를 성공이나 빠른 완료로 계산하지 않았다. 준비 대기 옵션이 모든 모델의 완료 보고 정확성을 보장한다는 뜻도 아니다.
- direct-b의 준비 후 후속 요청은 edit→read 순서로43을 정확히 저장·읽었지만 기존 검사에서 read 호출2개를 요구해 실패했다. 결과 개수 대신 실제 수정 완료 뒤 읽은 내용과 최종 바이트·다른 파일 보존으로 판정하도록 측정기를 고쳤다. 기존 실패 결과는 덮어쓰지 않고 `readback-reassessment.json`에 실제 근거를 별도로 남겼다. 위 direct-a 실패는 이 보정 후에도 실패다.
- guard 첫 검사에서 async 표시 누락으로 구문 오류가 났으며 수정 후 재실행했다.

## 승인 수명 검사

- Node40개 통과: 기존 좌표·정책·프로세스 수명·응답·전경 입력과 새 초기 준비/작업 승인을 포함한다. 별도 ACP guard 검사도 통과했다.
- Python18개 통과: 입력/출력 보존·실제 task 파일 전달·완료/취소/EOF·CUA 설치·읽기 검증 근거를 확인했다.
- 설치 OpenCode + ACP 실행기 + 모의 MCP/모델/승인 통합 시험에서 초기 a/c는 통과했으나 b/d/e/f는 연결 종료로 실패했다. 진단 로그로 Windows 상태 파일 교체의 WinError5를 확인했고, 제어 파일의 원자적 교체에만 최대0.5초의 짧은 재시도를 추가했다. 실제 GUI 입력은 재시도하지 않는다. 실패를 보존한 뒤 최종 수정본 g/h/i 세 회가 연속 통과했다. 같은 요청의 두 호출은 승인 횟수 `[1,1]`, 같은 채팅의 다음 요청은2가 되어 `[1,1,2]`였다. 실제 OpenCode 세션 메타데이터 전달도 확인했다. 이 시험은 실제 Windows 승인창 반복 클릭이나 GPU 코딩 품질 시험이 아니다.
- 설치 확장 회귀32개 실행에서는 이번에 변경하지 않은 일반 품질/언어 지침의 문구 검사9개 불일치가 남았다. 원문 로그를 보존했고 관련 없는 지침을 되돌리거나 검사를 삭제하지 않았다. 전체 회귀가 모두 통과했다고 주장하지 않는다.
- 이번 작업 단위 승인 방식의 실제 Rider GUI·Hermes·macOS 반복 입력은 미검증이다. 앞선 Windows 단일 동작 시험은 RIDER_RECHECK_20261023_KO.md에 별도로 남겼다.

## 설치와 증거

설정/ACP 엔트리/설치 파일은 백업 후 갱신했다. 모델·추론 수준·출력 한도·기존 사용자 MCP 실행 제한은 바꾸지 않았다. 진행 중 프로세스를 강제로 재시작하지 않았으며 다음 OpenCode 연결부터 적용된다. 초기 준비 옵션은 `tools/configure_acp_foreground_guard.py --mcp-startup-barrier-ms 15000`, ACP 수명 실행기는 `tools/configure_acp_compact_display.py`로 재설치할 수 있다. 푸시하지 않았다.

증거는 Strata-data/diagnostics 아래 `mcp-startup-*20261023*`, `task-approval-wire-20261023-a`, `task-approval-cache-20261023-a`에 보존한다. `measured-comparison.json`은 첫 요청 결과와 콜드 호출 수·원래 후속 실패·별도 재평가를 함께 기록한다.
