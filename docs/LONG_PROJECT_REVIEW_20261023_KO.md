# 장기 작업 제한·재시작·중지 재검사 및 적용

2026-10-23. 설치된 OpenCode 2.0.22와 격리된 CPU 모의 서버/새 DB를 사용했다. 실제 Strata/GPU 서버를 중단하거나 재시작하지 않았다. 실제 복잡한 프로젝트 완성, 장시간 모델 품질, Rider/Hermes UI, 외부 Windows/Mac/Linux, 실제 GUI 조작은 미검증이다.

## 단계 예산

한 ACP 요청 안에서 210번의 순차 write가 필요한 모의 작업을 구성했다. 각 단계는 이전 도구 결과 후 다음 모델 요청이 생성되는 실제 OpenCode 루프다. 모델은 스크립트 응답이며 일반적인 개발 품질 시험은 아니다.

| 예산 | 저장 완료 | 모델 요청 | 관찰 |
|---|---:|---:|---|
| 200 | 199/210 | 200 | 마지막 요청 tool_choice=none, 완료 문구 없음, 예산 중단 |
| 512 | 210/210 | 211 | LONG_PROJECT_COMPLETE 전달, 예산 중단 없음 |

각 1회. 경과 시간은 7.100초 / 7.594초였으나 두 번째는 다른 CPU 검사와 병행했다. 속도 향상 비교가 아니라 조기 중단 해소의 기능 증거다. 제한에 도달한 첫 시험도 의도한 중단 재현이므로 시험은 통과했다. 양쪽 ACP stopReason은 end_turn이므로 그것만으로 전체 업무 성공을 판단하면 안 된다.

현재 기본 OpenCode `agents.build.steps`를 200→512로 바꾸고 설치기를 `--build-steps 512`로 선택할 수 있게 했다. 미선택 설치기의 기본 200과 기존 사용자 지정값은 유지한다. 유효 범위는 1~10000 정수, 무한 반복은 지원하지 않는다. 지침에는 실제 설정 예산 우선과 중단 전 체크포인트를 유지했다. 이 설정이 전원/프로세스 중단 후 자동으로 새 ACP 요청을 생성하지는 않는다.

## 관리형 서버 재시작

설치된 OpenCode + 실제 외부 Supervisor + 소유 CPU 모의 모델 프로세스로 검사했다.

- 같은 ACP 세션 3회 재시작 / 6회 모델 요청: 소유 PID 교체, 인증된 준비 상태, 같은 요청의 후속 응답, end_turn 전 최종 전달 통과.
- 준비 실패 주입 1회 / 2회 모델 요청: native 도구 failed가 ACP에 표시되고 모델이 실패 결과를 받아 처리함을 확인.
- 관리 BAT 라우팅은 ON/OFF 각각 실제 CMD로 실행했다. 무선택 일반 경로, 명시 --managed, 선택 파일이 있을 때 관리 경로, 관리 자식이 다시 관리자를 만들지 않는 경로를 확인했다. Python 호출과 서버 시작 부분은 가짜 실행기로 대체했다. 실제 GPU BAT 시작 시험은 아니다.

효과가 확인된 관리 기능을 기존 BAT 이름으로 선택할 수 있도록 `--managed-launchers`와 로컬 선택 파일을 추가했다. 현재 PC의 실제 `C:\Users\luiny\Strata` ON/OFF BAT에는 해당 라우팅만 백업 후 삽입했고 선택 파일을 만들었다. 다음 정상 서버 시작부터 기존 ON/OFF BAT가 관리 모드로 실행된다. 현재 관리 밖의 서버는 그대로 뒀고 다른 프로세스를 가져오거나 강제 종료하지 않았다. 관리 포트가 현재 활성화됐다는 뜻은 아니다.

## 취소 — 실패 유지

- 첫 내용 수신 전 --cancel-stream: ACP cancelled 반환 이후 모의 상류 연결이 5초 안에 닫히지 않는 기존 문제를 다시 재현했다. 시험 종료 1.
- 첫 내용 수신 후 --cancel-stream-ready: 약 0.066초에 취소, 모의 연결 종료, 미완성 tool 미실행, 같은 세션 후속 요청 통과.

첫 실패를 후속 성공으로 대체하지 않았다. 근거 없는 폴링·빈 스트림 패킷·전체 서버 강제 종료를 적용하지 않았다. 설치된 바이너리의 조기 취소 경로는 미해결이며 위 결과가 실제 GPU 활동 종료를 증명하지 않는다.

## GUI와 CUA

GUI 작업은 기존 CUA 경로를 사용한다. 현재 창·스크린샷/element_token, 좌표 변환, 입력 후 상태 확인, 무응답/EOF 처리 검사를 다시 실행했다. 관련 Node 49개가 통과했다(출력 복구 및 재시작 도구 검사 포함). 추가 CUA 정책 검사 9개로 모든 입력 도구의 foreground 차단과 기본 background 고정을 확인했다.

실제 앱이 background 입력을 지원하지 않거나 UAC 보안 데스크톱이 나타나면 CUA 도구가 있다는 이유만으로 해결되지는 않는다. 사용자 포인터·키보드를 사용하는 경로를 허용하지 않았다. 필요한 GUI 단계는 미완료로 기록하고 독립된 허가 작업만 계속한다. 별도 데스크톱/VM 등 격리 환경의 실사용 검증은 이번에 하지 않았다. 모델이 미노출 도구를 호출한 자동 CUA 로딩도 계속 보류했다.
