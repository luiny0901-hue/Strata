# Low·Medium·High 추론 병목 측정 — 2026-10-25

이 문서는 revision22의 Medium 개선과 거부된 Low2,048 후보를 기록한다. 이후 revision23에서는 Low3,072 후보를 별도로 측정해 세 수준의 상한을 순서대로 설정한다. 현재 정책과 새 측정은 [추론 수준 보고서](REASONING_TIERS_20261025_KO.md)를 참고한다. 아래 원래 결과·실패 이력은 그대로 보존한다.

실제 실행 중인 Strata에서 같은 입력으로 각 수준의 추론 시작·첫 답변/도구 인자·완료 시각과 네이티브 프리필·디코딩 시간을 측정했다. 주된 대기는 추론 토큰 생성이었다. 연결 정지나 무한 대기 증거는 없었으며, 짧은 요청의 첫 추론까지 대체로0.1~0.3초, 디코딩은 대략120~130tok/s였다. 쉬운 문제에서도 수준 순서와 실제 추론량이 항상 일치하지 않았다.

측정 장비는 RTX3090Ti, Ryzen Threadripper3970X다. 현재 엔진의 `--tail-role-token`과 수준 전환 후 캐시 재사용을 확인했다. 서버·모델·GPU 설정은 재시작하거나 바꾸지 않았다.

## 채택한 변경

| 수준 | 변경 전 기본 추론 예산 | 변경 후 |
| --- | ---: | ---: |
| Low | 8,192 | 유지 |
| Medium | 8,192 | **4,096** |
| High | 8,192 | 유지 |

이는 생각하기를 끄거나 전체 출력·파일 크기·도구 인자 한도를 줄이는 변경이 아니다. 서버의 기존 `reasoning_budget_tokens` 경로로 추론을 마무리하고 답변·도구 인자를 계속 생성한다. 요청에 직접 지정한 예산은0·null을 포함해 그대로 두고 서버의 기존 해석에 맡긴다. 범용 플러그인은 기본적으로 예산을 바꾸지 않으며 코딩 프리셋만 `reasoningBudgets:{medium:4096}`을 활성화한다.

수동 Medium과 Default가 Medium을 선택한 경우에 적용한다. Low·High 수동 요청은 본문을 다시 직렬화하지 않는다. 압축·제목 등 보조 요청의 예산은 바꾸지 않는다. 최소 비용·제약 조합 문제를 단순 계산으로 잘못 분류하지 않도록 Default 분류도 보완했다. 어려운 추론을 명시적으로 하려면 High를 선택할 수 있다.

## 같은 약8K 입력에서의 결과

코딩 문제는 할인·배송비·음수·수량0 규칙을 가진 순수 함수를 생성했다. 저장 전에 AST로 실행 범위를 제한하고 기존7개 검사와49개 조합 경계값을 확인했다. 계획 문제는10개 모듈의 기능·비용·의존성을 입력해 최소 비용 조합을 구했으며,1,024개 경우를 독립적으로 전수 검사한 비용24를 정답으로 사용했다. 온도0·seed42, 전체 출력 상한12,288로 고정했다. 각 수준 안의 메시지 해시는 비교 전후 동일했다.

| 계획 문제 | 기존 완료 시간 중앙값 | 후보 완료 시간 중앙값 | 정답 |

Medium의 이 계획 문제 완료 시간은 약36% 줄었다. 추론 시작부터 첫 답변까지 중앙값도51.62초에서33.04초로 감소했다. 이는 표본이 적은 특정 검증 문제의 결과이며 모든 작업의 속도·정확도 개선을 보장하지 않는다.

일반 코드 문제의 Medium 중앙값은 기존3.08초·후보2.61초였지만 양쪽 모두 예산에 도달하지 않았다. 이 차이는 모델의 추론량 편차와 구분할 수 없어 예산 조정의 효과로 계산하지 않았다. 모든 저장 코드의 추가 조합 검사도 통과했다.

## 긴 입력과 연결 경로

실제 프롬프트245,344~245,374토큰에서 Low·Medium·High 기본 설정과 Medium 후보의 코드 생성·56개 검사가 통과했다. Medium 후보는 이 경우에도 예산에 도달하지 않아 단일 표본의 시간 차이를 성능 효과로 주장하지 않았다. 긴 입력에서 첫 추론까지 약1.5~1.9초와 디코딩 약110~113tok/s를 관찰했으며 캐시 처리·긴 입력의 비용으로 별도 기록했다.

설치된 OpenCode2.0.22 ACP를 통해 수동·Default 선택과 예산 전송을 확인했다. 이 연결 시험은 도구를 비활성화한 계산·후속 요청이며 실제 코드 품질 검사는 위 직접 Strata 생성 결과와 구분한다. Medium에는4,096이 전달되고 Low·High에는 새 예산이 강제로 추가되지 않는지 검사했다. 분류용 추가 모델 호출은 없다.

## 거부·실패 이력

- 최초 측정 스크립트의 `tokenizers` 모듈이 설치되어 있지 않아 실행 전 실패했다. 추가 설치 없이 저장소의 CPU 기준 토크나이저로 교체했다. 이 실패에서는 모델 요청을 보내지 않았다.
- Low1,024·Medium2,048은 계획 문제에서 각각 오답을 냈다. 축소 설정은 적용하지 않았다.
- Low2,048은 처음에는 정답이었으나 반복 시험3회 중1회 오답이 나왔다. 전체 후보 행렬이 이 지점에서 실패했고 Low 축소를 제외했다. 실패한 `validation-suite.log/json`을 성공으로 덮어쓰지 않았다.
- Medium4,096은 같은 계획 문제3회, 코드 문제3회, 긴 입력 코드1회에서 모두 검사를 통과했다. 이후 별도 `medium-validation.json`으로 긴 입력 기본 세 수준과 선택된 Medium 후보만 확인했다.
- 캐시 예열용 출력1토큰 요청은 의도적인 불완전 생성이며 정상 작업·정답 표본에 포함하지 않았다. 초기 완성 응답 예열도 성능 중앙값에서 제외했다.

추론 토큰 수는 저장한 추론 문자열을 같은 CPU 토크나이저로 다시 인코딩한 추정치다. 예산 마무리 문구 때문에4,096 예산에서 추정4,112토큰처럼 보일 수 있으며 서버의 정확한 단계별 카운터로 표시하지 않았다. 정답·오답과 실패·예열 원시 자료는 모두 보존한다.
