# Claude Code → OpenCodex → Strata 연결 지연 점검

2026-10-25, OpenCodex 2.92.0, Claude Desktop 내장 Claude Code 2.1.308, Strata Qwen3.8 Flash Next UD-IQ4_XS, RTX 3090 Ti, 262,144 컨텍스트 기준입니다. 실제 서버는 기존 8080이며 게이트웨이는 기존 10100입니다.

## 확인한 병목과 적용

기존 Strata 공급자는 `openai-chat` 방식이었습니다. Claude의 Messages 입력이 중간 형식과 Chat 형식으로 변환되면서 ToolSearch의 지연 로딩·도구 참조 정보가 일반 도구 목록으로 바뀌었고, 도구 검색 후 긴 프롬프트의 캐시가 끊겼습니다. Strata 직결은 같은 요청에서 이 캐시를 유지했습니다.

기존 관리 API로 아래 두 설정을 적용했습니다. 실행 중인 프록시에 바로 반영되어 서비스 재시작은 하지 않았습니다.

```json
{
  "providers": {"strata": {"adapter": "anthropic"}},
  "protocols": {"rollout": {"managedMessagesNative": true}}
}
```

`PATCH /api/providers?name=strata`와 `PATCH /api/protocols/settings`만 사용했습니다. Strata 주소 `/v1`은 기존대로이며 해당 어댑터가 `/v1/messages`로 정규화합니다. 다른 공급자, Desktop 3p 기본 모델과 주소, Claude 공통 권한·MCP는 유지했습니다. OpenCodex·Strata 엔진 코드를 패치하지 않았습니다.

관리 API의 계획 조회는 Messages → Messages, `mode:native`, `fidelity:preserved`로 확인됐습니다. 이 기능은 기존 OpenCodex의 opt-in 경로입니다. 검색 sidecar, 이미지 전처리, 합성 effort/fast 모델 행, 특정 정책 요청 등은 기존 변환 경로로 돌아갈 수 있습니다. `managedMessagesNativeOAuth`나 `directEncoders`를 추가로 켜지 않았습니다.

## 동일 요청 비교

표의 시간은 도구 검색 직후 요청에서 **첫 스트림 내용**까지입니다. 출력 상한 256, 사고 비활성, 동일 메시지·도구 정의를 사용했으며 생성된 호출은 실행하지 않았습니다. before/after의 프록시 요청 바이트 SHA-256이 각각 일치합니다. 각 요청 전 실제 Strata slot의 idle을 확인했습니다.

| 입력 크기 | 기존 변환 경로 | 원본 Messages 경로 | 감소 | 검색 후 캐시 재사용 |
|---|---:|---:|---:|---:|
| 약 3만 토큰 | 11.249초 | 1.232초 | 약 89.0% | 0 → 29,256토큰 |
| 약 25만 토큰 | 89.201초 | 2.416초 | 약 97.3% | 0 → 249,956토큰 |

약 25만 토큰의 **첫 cold 입력**은 기존 88.272초, 개선 후 87.675초였습니다. 처음 읽는 GPU 연산이 빨라진 결과는 아닙니다. 원본 입력을 유지한 채 도구 검색 뒤의 중복 프리필을 줄였습니다. 실제 새 경로의 입력은 249,963/250,644토큰으로, 별도 계산한 Strata 입력 수와 일치합니다. 기존 경로는 변환된 프롬프트가 250,352/251,051토큰이었습니다.

큰 입력의 반복 요청은 기존 1.819초, 새 경로 1.449초였습니다. 검색 후의 큰 개선과 구분하며 이 작은 차이는 반복 표본이 충분하지 않습니다. 처음 큰 입력을 읽는 약 88초, 긴 KV에 대한 연산, 실제 출력 생성 비용은 남아 있습니다.

기존 경로의 스트림 시작 입력 추정치는 큰 요청에서 94,466이었고 최종 실측은 250,352였습니다. 새 경로는 원본 Strata 시작 usage를 전달해 249,963을 표시했습니다. 이 결과만으로 Desktop GUI의 컨텍스트 표시나 전체 자동 압축을 검증했다고 하지는 않습니다.

## 실제 코드 작업과 기능 보존

Desktop 내장 실행 파일과 Desktop 3p의 Strata wire model을 사용했습니다. 사용자 공통 지침·MCP를 로드하고 다음 세 작업을 같은 세션에서 수행했습니다.

| 작업 | 기존 경로 | 새 경로 |
|---|---:|---:|
| 파일 두 개 읽기, MCP 상태 확인, 결과 저장·재확인 | 21.306초 | 24.393초 |
| 같은 대화에서 결과 수정·재확인 | 11.495초 | 12.864초 |
| 계산 코드 수정·기존 테스트 실행 | 15.288초 | 16.326초 |

이 짧은 작업들의 총시간 향상은 확인되지 않았습니다. 기존 첫 요청은 13,332토큰이 이미 캐시된 상태였고, 새 경로의 첫 요청은 cold였습니다. 생성 내용과 호출 수도 달랐으므로 동일 조건의 전체 작업 성능 향상률로 계산하지 않습니다. CLI 시험은 요청마다 실행 파일을 다시 시작해 실제 상주 Desktop과도 다릅니다.

두 경로 모두 결과 파일·계산 테스트 4개 assertion·보호 파일 SHA-256이 통과했습니다. 기존 12회·새 경로 14회의 실제 API 요청은 모두 200이었습니다. 새 경로에서는 모델이 PowerShell의 설명 인자에 잘못된 XML 조각을 넣은 호출 1회가 실행 전 검증에서 거절됐고, 정상 인자로 재시도한 명령만 실행되어 테스트가 통과했습니다. 이를 무오류 시험이나 통신 중복 실행으로 표시하지 않습니다.

- Low·Medium·High 각각에서 사고 블록·지정 도구 이름·정수 인자 42가 정상 전달됐습니다. 캐시 조건이 서로 달라 이 시험의 시간으로 추론 단계 속도를 비교하지 않습니다.
- 잘못된 sampling 타입은 HTTP 400으로 반환됐습니다.
- 생성 중 연결을 끊자 Strata 엔진 `cancel=True`, slot idle을 확인했습니다. 종료 후 idle과 cancel 로그 확인까지 약 0.435초였고(로그 기록 대기 0.2초 포함), 같은 metadata 세션의 후속 요청은 `OK`로 성공했습니다.
- Chat Completions와 Responses 입구도 각각 200과 `OK` 응답을 확인했습니다.
- 다음 자가진단을 위해 `environment_status`/`doctor`에 읽기 전용 계획 미리보기와 OpenCodex 최근 요청 기록 조회를 추가했습니다. 이번 점검에서는 같은 최근 12건 결과를 표면별로 나누어 CLI(`claude`) 기록 8건, Desktop(`claude-desktop`) 기록 0건으로 확인했습니다. 따라서 당시 중앙 지연 1,796.5ms와 첫 출력 10ms는 CLI 표본이고 Desktop Code 실측으로 볼 수 없습니다. CLI 최근 8건 중 6건은 200, 계획된 잘못된 sampling 검사 1건은 400, 의도적 취소 1건은 499였습니다. 최신 CLI 요청은 입력 26,724토큰 중 26,025 캐시 적중, 완료 4,144ms·첫 출력 15ms였습니다. 이후 갱신한 MCP를 통해 새 Claude Code CLI 상태 호출을 완료했고, 응답에서 CLI 8건/성공 6건·Desktop 0건을 구분했습니다. 호출 후 읽은 표본은 CLI 8건/성공 7건, 중앙 지연 3,117ms·첫 출력 18ms였습니다. 최신 입력 26,778 중 26,021이 캐시였고, 완료 3,045ms·첫 출력 15ms였습니다. 표본이 계속 바뀌며 요청 구성이 달라 직접 성능 비교는 하지 않습니다. 응답에 경로·시간·상태·토큰 수만 남기고 프롬프트·응답·헤더·요청 ID는 제외합니다.
- `doctor` 계획과 로그는 구성/최근 요청 근거이며 모든 미래 요청의 경로를 보장하지 않습니다. 전체 읽기 전용 diagnose 7회는 중앙값 100.54ms, 최대 143.71ms였습니다. 공통 설정 재적용이 네이티브 전송 설정을 되돌리지 않는 회귀 검사도 유지합니다. 이번 회차 source helper 검사 23개와 설치본 helper·maintenance 검사 34개가 PASS입니다. 리다이렉트 시 관리 토큰 미전달과 256KiB 초과 로그 응답 거부도 검사했습니다.
- ON/OFF 생성 프로필의 `anthropic_tool_cache:true`, `fit_max_tokens:true`, `effort_position:end`를 확인했습니다. 실제 부하는 현재 실행 중인 ON 서버에서만 수행했습니다.

## 실패·재시도와 제외 범위

- 어댑터만 Anthropic으로 바꾼 첫 후보는 검색 후 11.009초, 캐시 0으로 병목을 해결하지 못해 되돌렸습니다. 이후 기존 원본 Messages 옵션까지 적용한 후보에서 개선됐습니다.
- 설치 npm 패키지에 루트 AGENTS.md/구조 문서가 없었고 일부 추정 경로 조회가 실패했습니다. 패키지 JSON의 첫 읽기는 Windows 기본 cp949로 실패해 UTF-8로 읽었습니다. OpenCodex 소스는 수정하지 않았습니다.
- 첫 CLI 시험은 전역 settings의 주소가 시험용 환경변수보다 우선해 기록 relay를 우회했습니다. 기능 통과만 보존하고 구간 측정으로 사용하지 않았습니다. 이후 세션 한정 `--settings` 주소로 계측을 고쳤습니다.
- 다음 relay 시도는 짧은 Desktop 접속 표식이 본문의 일반 단어와 일치해 비밀 값 검사에서 오탐 중단됐습니다. 공급자 실제 비밀 키만 검사하고 기존 공개 loopback 표식으로 연결해 재시험했습니다. 키 원문을 출력하지 않았습니다.
- 잘못된 지정 도구 이름을 400으로 거절할 것으로 기대한 시험은 실패했습니다. 실제 설치 fork는 문서화된 기존 정책으로 로그를 남기고 auto로 돌아갑니다. 직결과 프록시 모두 같은 동작이며 선언된 진단 도구만 출력됐습니다. 연결 최적화에서 이 엔진 정책을 변경하지 않았습니다.
- Responses 첫 연결 확인은 모델이 `OK.`를 출력해 과도한 문자열 일치 조건에서 실패했습니다. 원본 기록을 보존하고 입구 전달 기능을 확인하는 시험으로 다시 수행했습니다.
- GUI의 직접 화면 반응 시간·버튼 완료 표시, 실제 Desktop 세션 자동 압축, 262K에서 수정 두 번 수행, 다중 사용자 경쟁·장시간 무인 운영·업데이트/재부팅은 이번 측정 범위가 아닙니다. 25만 토큰 시험은 실제 프리필·생성이지만 준비된 요청 재생이며 도구 실행은 하지 않았습니다.
