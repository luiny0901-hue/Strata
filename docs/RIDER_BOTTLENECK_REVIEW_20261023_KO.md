# Rider 자율 코딩 경로 점검

2026-10-23. 실행 중인 프로세스, 설치 설정과 OpenCode 2.0.22 소스를 읽었다. 새 부하 시험이나 GUI 조작, 서비스 재시작, 설정 변경은 하지 않았다. 아래는 병목 후보와 이미 확인된 제약이며 새 성능 향상 측정 결과가 아니다.

## 우선순위

| 순위 | 관찰 | 영향과 개선 방향 |
|---|---|---|
| 1 | Rider OpenCode PID 32852 및 CUA PID 33172는 09:39 시작, 새 CUA 파일은 10:06 설치 | 현재 연결에는 승인 도구가 없다. 진행 중인 작업을 끝낸 뒤 연결을 다시 시작해야 한다. 파일 설치만으로 실행 중인 모듈이 교체되지는 않는다. |
| 2 | REA 실행 timeout 및 MCP 전역 timeout 미설정 | 설치 소스의 기본 실행 제한은 12시간이다. 도구가 응답하지 않을 때 긴 대기 후보다. REA의 긴 분석 작업과 가벼운 조회를 구분한 제한·진행 상황·취소 전달을 도입할 필요가 있다. 모든 REA 작업을 일괄 짧게 끊으면 정상 분석을 중단할 수 있다. |
| 3 | 승인 전경 입력은 동작마다 확인창과 별도 CUA 초기화·화면 조회를 거침 | 짧은 클릭·타이핑 연속 작업에는 승인·초기화 비용이 누적된다. 사용자 동의가 있다면 정확한 창·짧은 유효 시간·작업 범위에 묶인 승인 방식이 개선 후보다. 현재는 동작 1회 승인만 제공한다. |
| 4 | 승인 전후 PNG 해시가 완전히 같아야 전경 입력 허용 | 시계·깜박이는 커서·애니메이션만 변해도 미실행으로 돌아갈 수 있다. 단순 이미지 일치 대신 창 소유자·좌표 프레임·대상 컨트롤의 동일성을 확인하는 방식이 개선 후보다. 비교를 무조건 생략하면 잘못된 클릭 위험이 생긴다. |
| 5 | build.steps=512는 유한한 한 요청 예산 | 긴 작업의 조기 중단을 줄이지만 예산 소진·Rider 연결 종료·재부팅 이후 자동 재개를 제공하지 않는다. 지속 실행에는 중지 의사를 보존하는 체크포인트와 명확한 재개 소유자가 필요하다. |
| 6 | 기존 기록에서 첫 스트림 내용 이전 취소가 상류를 닫지 못한 실패가 남아 있음 | 사용자 중지 후 모델 작업이 남는 병목 가능성이다. 실제 엔진 취소·유휴 상태까지 연결한 검증이 필요하다. 이번에는 사용자 서버를 취소하거나 부하를 주지 않았다. |

## 현재 유지할 부분

- 실행 중 strata.exe PID 29212에 `--tail-role-token`이 있어 추론 수준 전환 캐시 보존 옵션이 적용돼 있다.
- 서버 8080과 관리 포트 8768 리스너가 있다. 이것만으로 응답 속도나 복구 성공을 판정하지 않는다.
- context 262144, output 32000, 자동 압축 활성, buffer 65536, keep.tokens 12000이다. 현재 소스의 압축 상한 계산은 context에서 buffer를 빼므로 기본적으로 약196608 토큰 부근에서 압축 필요성을 판단한다. 매 요청을 262K까지 채워야 압축하는 설정은 아니다.
- Rider ACP는 생각 알림을 줄이는 래퍼를 사용한다. 일반 답변·도구 결과·승인·최종 응답은 필터 대상이 아니다. 설치만으로 실제 화면 렌더링 개선률을 단정하지 않는다.
- 기존 파일 I/O 기록은 ms 단위, 모델 작업은 초 단위다. 현재 근거로 SSD 캐시나 파일 저장 구조를 더 복잡하게 바꿀 이유는 부족하다. 부분 읽기·부분 수정·독립 조회 묶음을 유지하는 것이 타당하다.
- 지침 3개는 합계35523바이트다. 바이트 수만으로 지침이 주 병목이라 판단할 수 없으며, 중복 제거는 기능·권한·취소 규칙을 보존하며 해야 한다.
