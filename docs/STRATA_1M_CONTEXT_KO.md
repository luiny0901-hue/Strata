# 1M ON/OFF 실행

기존 262,144 실행기와 별도로 다음 파일을 사용한다. 같은 8080 포트와 기존 supervisor를 사용하므로 동시에 실행하지 않는다. 작업을 마치고 서버를 정상 종료한 뒤 원하는 실행기를 선택한다.

- `run-unsloth-ud-iq4_xs-nvfp4-fork-uncensored-on-1m.bat`
- `run-unsloth-ud-iq4_xs-nvfp4-fork-uncensored-off-1m.bat`

1M은 1,048,576토큰이다. 기존 템플릿에서 별도 `-1m.json` 프로필과 로그를 생성하고 `--max-context 1048576 --rope-scaling dynamic --rope-scale 4`를 적용한다. 262K 안에서는 학습 때의 위치 계산을 유지하고, 그보다 길어지면 필요한 배율의 YaRN으로 확장한다. 최대 배율은 4다. `rope_auto`를 통해 설치된 서버의 기존 호환성 검사와 필요 시 정적 YaRN 선택을 재사용한다. 같은 UD-IQ4_XS 모델·Pack·MTP·int8 KV·KV resident 32768과 GPU 선택을 재사용하며, VRAM 여유는 아래에서 기록한 조정 값(예비 768MiB, 청크 8192)을 ON·OFF 템플릿에 함께 적용한다. 현재 PC는 GPU 1 RTX 3090 Ti 한 장이다. ON/OFF의 거부 투영 차이와 기존 캐시 정책은 유지한다.

모델의 학습 길이는 262,144이므로 1M은 실험적인 RoPE 확장이다. 기동·API 처리 성공은 모든 장문 코딩의 품질이나 장기 무인 실행을 보장하지 않는다. 원래 실행기는 RoPE 확장을 추가하지 않는다.

## VRAM 여유 조정 — 2026-11-01

262K·1M 실행 모두에서 응답 중 엔진이 종료 코드 1로 끝나고 잠시 후 다시 읽어 올라가는 일이 반복됐다. 엔진 로그의 마지막 오류는 `prefill copy_i32: an illegal memory access was encountered`였고, 기동 시 `357MiB of VRAM free` 상태였다. 요청 시작에도 357MiB를 알리며 #2065(WDDM이 GPU 메모리를 시스템 RAM으로 페이징하면 창이 끝나지 않는다)를 권장했다. 같은 로그에서 엔진이 직접 제시한 값대로 ON·OFF 템플릿의 `--vram-reserve-mib`를 448에서 1152(1차)로, 재측정 후 엔진이 요청 시작 961MiB에서 권장한 1216으로 올리고, `--prefill`을 16384 청크(ON은 `auto:16384`, OFF는 `auto`가 16384로 결정)에서 `auto:8192`로 바꿨다. 최종 값은 아래 경계 측정 후 768로 확정했다. 전문가 캐시가 약 700MiB 줄어 디코딩 히트율이 조금 내려가지만, 0에 가까운 VRAM에서 페이징으로 무너지는 것보다 낫다는 엔진 문서의 실측(4080 SUPER, 453슬롯 차이가 7배)에 따른다. 실행기는 `C:\Users\luiny\Strata`를 참조하므로 같은 값의 미러를 그 체크아웃 템플릿에도 반영했다.

1152로 재시작한 262K 실행에서 실측한 결과: 기동 시 VRAM 여유 357→1061MiB, 검증 창 확보 후 961~1,061MiB, 전문가 캐시 6729→6429슬롯(예측대로 약 -300), 프리필 청크는 8192로 적용되어 프롬프트 경로 슬롯 사용이 3441→2097개로 줄었다. 캐시가 비워진 상태에서 134,028토큰을 처음부터 끝까지 재시작 없이 읽었고(2,802 tok/s), 후속 요청은 134,523토큰을 재사용하며 디코딩 94 tok/s를 유지했다. 1216에서는 기동 시 여유 1,127MiB, 검증 창 확보 후 1,057MiB였고 요청 시작 "below 1024 MiB" 안내가 뜨지 않은 채 144,204토큰 프롬프트가 재시작 없이 끝났다(2,805 tok/s). 1M도 같은 템플릿이므로 렌더 결과에서 같은 값을 확인했다.

같은 날 기동 시 여유와 예비 값의 관계가 선형(여유 = 357 + (예비 − 448), ±2MiB)임을 확인하고 512~1216 경계 측정을 거쳐 768로 확정했다. 512는 여유 423MiB에서 58,533토큰 읽기 중 illegal memory access로 크래시, 640은 549MiB에서 약 190K통과 후 109,395토큰 읽기 중 크래시, 768은 679MiB에서 두 번의 재시작 모두 통과·크래시 0건이었다. 1024는 935MiB, 1152는 1,061MiB, 1216은 1,127MiB로 모두 통과했다. 전문가 캐시는 512에서 6,704슬롯, 640에서 6,648, 768에서 6,594, 1024에서 6,481, 1152에서 6,429, 1216에서 6,400(448 기준 6,729)였다. 768 확정 실행은 223,610토큰 세션 재프리필(83.4초, 2,679.6 tok/s)과 262K 프롬프트(2,628.6 tok/s), 58,533(2,734.5), 109,395(2,806.9)를 재시작 없이 통과했다. 679MiB는 엔진이 요청 시작에 확인하는 1,024MiB 아래이므로 768에서는 "below 1024 MiB" 안내가 부팅마다 한 번 뜨며, 이것이 이 값의 예상 동작이다. 안내 자체를 없애려면 엔진 권장인 1152 이상으로 되돌리면 된다. 경계(549MiB 크래시 / 679MiB 통과)는 같은 날 한 PC의 근거이므로 GPU 부하가 다른 기기나 사용에서는 다시 확인이 필요하다.

1M 실행기에서도 768로 확인했다(2026-11-01). 기동 시 여유는 675MiB로 262K의 679MiB와 같은 수준이었고, 1M KV가 자리를 잡아 전문가 캐시는 5,999슬롯(13.52GiB, 262K에서는 6,594)으로 줄었다. 단일 프롬프트 269,553토큰을 차가운 상태에서 끝까지 읽었고(103.9초, 2,593 tok/s, 262,144위치 너머에서 동적 YaRN 배율 1.125 적용, 회전 표 116.7ms), 같은 부팅에서 137,847토큰 세션 재프리필(2,840.2 tok/s)과 58,533·109,395토큰 차가운 프롬프트를 번갈아 처리하는 동안 재시작과 `illegal memory access`이 0건이었다. 요청 시작 "below 1024 MiB" 안내는 768에서 예상대로 부팅당 한 번 떴고, 디코딩은 프롬브 146.5 tok/s로 262K와 같은 대역이었다. 전환 시 클라이언트 동기화도 동작해 저장 컨텍스트가 1,048,576으로 반영됐고(백업 보관, 새 클라이언트 세션부터 반영) 전환 자체는 기존 supervisor를 멈추고 1M 배트를 실행해 이루어졌다.

#### 설정 A/B 벤치 — 2026-11-01

같은 엔진·같은 날, 저장소 텍스트로 만든 고정 프롬프트(50,881·58,533토큰, 온도 0, 재시작 후 첫 요청 = 차가운 프리필)로 A(448+auto:16384)와 B(1216+auto:8192)를 번갈아 부팅해 측정했다. 프리필: 50,881토큰 A 2,823.8/2,832.2 → B 2,645.8 tok/s, 58,533토큰 A 3,139.5/3,141.1 → B 2,738.1 tok/s — B가 6.6~12.8% 느리다. 차이는 프리필 청크(16384→8192)에서 나오며 50K 프롬프트 한 번에 약 1.2초, 58K에 약 2.8초가 늘어난다. 디코딩: 같은 목록 생성 프롬프트(약 700~860토큰) 기준 A 139.6 → B 143.5 tok/s로 차이 없음(캐시 330슬롯 감소의 영향은 잡히지 않았다). 프리필 속도는 예비 512~1216 전체에서 동일했고(2,623~2,810 tok/s) 768 확정 재측정도 같은 수준(2,628.6~2,806.9 tok/s)이었으므로, 차이는 전적으로 청크 8192에서 나온다. 448의 크래시 재현 조건(여유 357MiB) 대비 768은 679MiB이므로, 이 프리필 비용은 크래시·재프리필 방지를 위한 비용으로 판단해 유지한다. 엔진은 1,024MiB 미만에서 `--prefill auto:8192` 또는 큰 `--vram-reserve-mib` 중 하나만 권하며, 1216+16384 조합은 이 PC에서 크래시 이력이 없어 시험하지 않았다.

## 클라이언트 동기화

처음 1M 실행 시 기존 관리 실행기 선택 표식을 활성화한다. 이후 원래 262K 실행기로 돌아가도 관리 실행과 컨텍스트 동기화가 유지된다.

관리 실행기는 시작·재시작 때마다 READY를 확인한 뒤 기존 클라이언트 설정 소유자를 한 번 호출한다. 실제 `/health`와 `/props`의 모델·컨텍스트·출력 기본값·비전 활성 여부를 OpenCodex에 반영하고 로컬 Claude의 모델·출력·압축 창을 갱신한다. 다른 공급자·MCP·권한은 재설정하지 않는다. 서버 소유자가 명시한 로컬 주소와 기존 키 파일은 함께 확인한 뒤 Strata 공급자에만 반영한다. OpenCodex의 공급자 편집 API가 Codex 카탈로그를 갱신한다. 적용된 Claude Desktop 게이트웨이 프로필의 새 모델 항목과 `supports1m/prefer1m`도 기존 Desktop 관리 API로 갱신한다. 모호한 쓰기를 자동 반복하지 않는다. 클라이언트 설정 동기화가 실패해도 READY 서버가 이미 받은 업무를 중단시키지 않도록 서버는 유지하고 콘솔 경고와 supervisor 폴더의 `client-context.json`에 실패를 남긴다. `status=synchronized`가 확인되기 전 클라이언트 설정까지 성공했다고 판단하지 않는다.

전환 시 지원하지 않는 설정·Codex 전역 덮어쓰기를 먼저 확인하고, OpenCodex 공급자와 Codex 카탈로그·Desktop 프로필을 확인한 다음 로컬 Claude 설정을 게시한다. 원격 응답이 유실되거나 Desktop 갱신이 실패하면 로컬 설정을 먼저 앞당기지 않고 실패 단계(`provider`, `codex_catalog`, `desktop`, `local_settings`)를 남긴다. 다른 소유자가 이미 받은 변경은 남을 수 있으므로 자동 재전송·임의 원복은 하지 않는다. 상태는 한 번씩 조회하고 관리 요청은 각각 20초 이내로 제한해 90초인 상위 동기화 제한 안에서 실패를 보고할 여유를 둔다. Codex 카탈로그의 자동 압축 기준도 양수이며 모델 창 안에 있는지 확인한다. Claude에서 다른 공급자의 모델을 선택한 상태라면 Claude 설정 파일은 보존하고 Strata 공급자·카탈로그만 갱신한다(`claude_selection=another_model_preserved`).

| 대상 | 262K 실행 | 1M 실행 |
| --- | ---: | ---: |
| Strata 및 OpenCodex 모델 창 | 262,144 | 1,048,576 |
| Claude CLI 사용자 지정 모델 창 | 262,144 | 1,048,576 |
| Claude 자동 압축 설정 창 | 262,144 | 1,000,000 |
| Codex 카탈로그 압축 기준 | 235,929 | 943,718 |
| 출력 기본 상한 | 32,000 | 32,000 |

Claude 압축 창의 공식 최대값은 1,000,000이다. 내부 출력·요약 버퍼를 중복 차감하지 않는다. Desktop의 1M 선택은 네이티브 모델 별칭으로 1,000,000을 보고할 수 있다. 모델 창·압축 설정 창·실제 압축 시작점은 같은 의미가 아니다. 입력과 출력 합계는 서버 창 안에 들어야 한다.

1M에서 262K 실행기로 되돌리면 새 세션부터 표의 262K 값이 적용되지만, 되돌리기 전에 262K를 넘게 쌓은 열린 세션은 자기 창이 여전히 1M이므로 압축이 먼저 걸리지 않고 전체 프롬프트를 보내 HTTP 400 `request exceeds the context window … requests are never truncated`를 받는다. 이 거부는 서버가 요청을 처리하기 전에 끝나 엔진과 다른 요청에 영향이 없고, 그 세션은 압축하거나 새로 열기 전까지 같은 거부가 반복된다(2026-11-01 실측: 262K 서버에서 269,553토큰 단일 프롬프트가 400으로 거부됐고 곧 이은 50,881토큰 요청은 200으로 정상 처리, 재시작 0건). 262K에서 1M으로 가는 쪽은 창이 넓어지므로 같은 거부가 나오지 않는다.

전환 뒤 새 클라이언트 세션을 연다. Claude Desktop은 필요하면 재실행하고 새 Code 세션에서 1M 선택을 확인한다. Codex 카탈로그는 시작 시 읽으므로 앱을 재실행하거나 새 실행에서 모델 정보를 읽어야 한다. 진행 중 세션의 한도를 바꿨다고 간주하지 않는다. 외부 접속 PC는 그 PC의 기존 클라이언트 설치 폴더에서 `python -m tools.strata_client_settings --sync-context`를 실행한다. 서버 PC가 외부 PC 설정을 변경하지 않는다.

### 모델·서버 설정을 바꿀 때

관리 실행기의 `--sync-client-context`는 현재 `--sync-runtime` 경로를 사용한다. 특정 모델 이름과 262K/1M 값에 동기화를 고정하지 않는다. 모델 이름은 소유한 프로세스의 health와 모델 목록에서 확인한다. 실행기에서 포트를 바꾸는 경우 supervisor의 `--server-url`도 실제 기동 주소에 맞춰야 한다. 명시적인 `--model`을 지정하면 그 모델이 일치할 때만 READY로 처리한다. 기존 ON/OFF·1M 실행기의 모델·포트·GPU·엔진 설정 자체는 이번 변경으로 바꾸지 않는다.

이미 준비된 로컬 서버에 수동으로 반영하려면 설치 폴더에서 `python -m tools.strata_client_settings --sync-runtime`을 실행한다. 기본값은 OpenCodex에 저장된 로컬 Strata 주소다. 임의의 다른 서버를 찾거나 연결을 재시도하는 상시 감시 프로세스는 추가하지 않는다. 외부 PC의 설정 파일을 서버 PC가 대신 수정하지 않는다.

컨텍스트가 100,000 미만이면 Claude 압축 설정은 기존 `auto` 방식을 사용한다. 더 큰 창도 Claude의 압축 설정 한도는 1,000,000이며 Desktop의 모델 표시는 네이티브 별칭과 1M 선택 규칙을 따른다. 모든 앱이 서버 숫자를 화면에 똑같이 표시한다는 뜻은 아니다. 서버가 별도 출력 기본값을 보고하면 그 값을 전달하고, 무제한 기본값(-1)이면 기존 정책인 `min(32000, context/4)`를 사용한다. 추론 단계는 현재 Strata Anthropic 연결의 Low·Medium·High 정책을 재사용한다. GPU·KV·캐시·프리필·RoPE·샘플링 등 엔진 설정은 서버가 실행하며, 클라이언트별 명시적 요청값의 우선순위는 보존한다. 다른 모델/엔진의 실행 지원과 품질까지 자동으로 검증하는 기능은 아니다.

## 전환 시 자동 압축 — 2026-11-01

위 400 거부가 반복되는 세션은 `tools/strata_session_compact.py`로 정리할 수 있다. 지금 떠 있는 작은 창 서버에서 그 세션을 요약한 뒤 세션 파일에 네이티브 압축 경계를 추가해 같은 세션을 이어서 쓰게 한다. 기본은 시험 실행(dry-run)이고 `--apply`만 실제로 쓴다. 특정 세션은 `--session-id`로 고르고, 응답 예약(`--reserve`, 기본 49,152)과 묶음 크기(`--chunk-tokens`, 기본 150,000)를 조절한다. 대상은 그 프로젝트에서 60분 이상 조용하고 256KB를 넘는 대기 중 세션이며 한 번에 최대 10개까지 본다. 결과는 콘솔에 각 줄로 표시하고 `--receipt`를 주면 JSON으로 남긴다.

쓰기 전에 원본 파일을 `%LOCALAPPDATA%\Strata\session-compacts\`에 복사하고, 세션 파일에는 두 줄만 추가한다. 기존 줄은 바꾸지 않는다. 추가하는 두 줄은 보존 구간이 없는 `compact_boundary` 기록(경계 이전 기록을 모두 버리는 뜻)과 표준 요약 접두어로 시작하는 요약 사용자 메시지다. 묶음은 앞 요약문과 함께 순서대로 요약하고, 요약문 자체가 창에 들어가지 못하면 건드리지 않고 건너뛴다.

사용 설정은 `~/.config/strata/server-control/session-compact.enabled` 파일 기준이고, 있으면 관리 실행기가 READY 확인 후 백그라운드 스레드에서 `--apply`를 한 번 실행한다. 결과는 supervisor 상태 폴더의 `session-compact.json`에 남는다. 파일이 없으면 기존 기동 경로와 동일하다. 이미 떠 있는 supervisor 프로세스는 설치된 코드를 다시 읽지 않으므로, 기능 설치 후 첫 자동 실행은 다음 번 컨텍스트 전환처럼 관리 실행기 프로세스가 다시 시작될 때 일어난다.

검증: CPU 검사 9개와 supervisor 검사 25개가 통과했다. 실제 262K 서버에서 합성 세션 282,000토큰을 6단계 요약으로 326토큰 요약문까지 압축하고 추가된 기록을 다시 읽어 형식을 확인했으며, 같은 명령줄의 시험 실행은 대기 중 세션 10개가 모두 창 안임을 확인하고 종료했다(2026-11-01). 경계 형식은 설치된 2.1.308 로더의 파일 검사에서 보존 구간이 없으면 전체 폐기 방식으로 인식되는 것을 근거로 삼았고, 터미널 CLI 재개로 끝까지 이어 붙이는 검증은 이 PC의 터미널 경로 로그인 문제가 있어 하지 못했다.
