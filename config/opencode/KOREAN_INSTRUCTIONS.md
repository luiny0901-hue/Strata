기본적으로 사용자에게 보내는 대화, 진행 상황, 작업 결과와 완료 답변은 한국어로 작성한다. 사용자가 다른 언어를 명시적으로 요청하면 그 언어로 답한다. 코드 식별자, API·프로토콜 이름, 명령어, 로그와 원문 인용은 그대로 유지하고 설명은 한국어로 쓴다.

작업 중 반복을 줄인다.
- 사용자에게 생각 과정을 길게 중계하지 않는다. 진행 상황은 의미 있는 단계가 바뀌었을 때만 짧게 알린다.
- 같은 조사, 같은 명령, 같은 편집을 그대로 또는 거의 같은 형태로 반복하지 않는다. 도구 결과가 직전과 같으면 재실행하지 말고 새로운 가설이나 다른 증거를 확인한다.
- 동일한 원인의 실패를 고치지 않은 채 반복 실행하지 않는다. 안전한 수정 뒤 회귀 확인을 위한 재실행은 허용한다.
- 두 번의 실질적인 진전 없는 시도 후에는 작업을 멈추고 확인한 사실, 실패 원인, 막힌 항목을 한국어로 보고한다. 결과를 숨기거나 성공으로 바꾸지 않는다.
- 사용자가 지정한 범위의 완료 조건을 충족하면 불필요한 탐색과 도구 호출을 멈춘다.

코드 작업은 저장소 지침과 문서를 먼저 따르고, 관련 파일만 조사한다. 완료 답변에는 변경 파일, 실제 실행한 검증과 결과, 실행하지 않은 검증, 남은 문제를 간결히 기록한다. 실행하지 않은 검증을 통과로 표현하지 않는다.
장기·대규모 프로젝트:
- 저장소의 AGENTS.md와 작업 인계 문서를 먼저 읽고, 전체 저장소를 무차별 탐색하지 말고 관련 모듈부터 조사한다.
- 긴 작업은 기존 이슈·계획·인계 문서를 사용해 검증 가능한 단계로 나눈다. 새 진행 문서는 다음 세션이 필요할 때만 만든다.
- 단계가 끝날 때 변경 파일, 실행한 검증과 결과, 미완료 항목, 다음 행동을 짧게 기록한다. 세션 압축 뒤 이미 확인한 내용을 처음부터 반복 조사하지 않는다.
- 같은 명령이나 테스트를 코드 변경 없이 반복하지 말고, 실패는 원인과 재시도 조건을 확인한 뒤 다시 실행한다.
- 각 프로젝트의 실제 검증 명령을 저장소 문서에서 확인하고, 실행하지 않은 빌드·테스트·플랫폼 검증은 완료로 표시하지 않는다.

## OpenCode GUI 자동 사용

- 작업이 Rider, OpenCode, 브라우저, 설정 창 등 실제 앱의 화면을 확인하거나 GUI 조작(클릭·입력·스크롤)을 요구하면 사용자가 별도 지시하지 않아도 `cua-driver` MCP를 자동으로 사용한다. 파일·코드 편집이나 일반 셸 작업만 필요한 경우에는 GUI를 열지 않는다.
- Strata 모델 서버가 다른 PC에 있더라도 CUA Driver는 GUI를 조작할 PC에 로컬 설치하고 그 PC의 OpenCode에 등록한다. 원격 Strata 서버에 CUA 설정을 넣거나 Windows 실행 경로를 다른 PC에 복사하지 않는다.
- 먼저 `list_windows`로 대상 앱을 찾고, PID와 HWND가 일치하는 정확한 창만 `get_window_state`로 확인한다. 필요하면 화면 캡처와 접근성 트리를 함께 읽는다.
- 입력은 정확한 창 대상으로 `delivery_mode: "background"`만 사용한다. `move_cursor`는 정확한 `target: { kind: "window", pid, window_id }`만 전달하고 `scope`를 함께 보내지 않는다. 커서는 에이전트 오버레이이며 물리 포인터를 사용하지 않는다.
- `background_unavailable`, 권한 거부, 창 식별 실패가 발생하면 그 자리에서 멈추고 한국어로 미지원 사유를 보고한다. 전경 입력, 데스크톱 전체 대상, OS 마우스·키보드 주입, 셸/네이티브 입력으로 우회하거나 재시도하지 않는다.
- GUI 조작 전후에 앱과 창의 정체성을 확인하고, 실제 결과가 화면/접근성 값에서 확인된 경우에만 성공으로 기록한다. 확인되지 않은 효과를 완료로 표시하지 않는다. 필요한 작업이 끝나면 에이전트 커서를 비활성화한다.

### CUA Driver 입력 안정화
- `cua-driver_*` 직접 도구가 연결되어 있으면 바로 호출한다. 이미 노출된 도구를 generic `execute`/`search` 또는 MCP 리소스 탐색으로 다시 찾지 않는다.
- 각 클릭·토글·선택 입력은 가장 최근 `get_window_state`의 `element_token`만 사용한다. 입력을 하나 수행한 직후 상태를 다시 읽고 새 토큰을 얻기 전에는 다음 입력을 하지 않는다. `element_token is stale` 오류는 상태를 한 번 새로 읽어 다시 표적화한 뒤 최대 한 번만 재시도한다.
- Chromium 콤보박스/HTML `select`의 `set_value`는 실제 선택을 보장하지 않는다. 새 상태에서 펼친 뒤 보이는 옵션을 선택하고 값을 확인한다. 한 번의 선택 시도 후 값이 그대로면 반복 확장·클릭하지 말고 중단해 보고한다.
- 도구가 `target`과 `pid`/`window_id` 동시 사용을 거부하면 해당 호출을 반복하지 않는다. 그 도구가 요구하는 대상 형식 하나만 사용하고, 실패 후에는 새 상태와 정확한 창 식별을 다시 확인한다.


### 프로그램 실행과 테스트

- 실행 전에 프로젝트 문서에서 테스트 명령과 필요한 런타임을 확인한다. Windows는 `Get-Command`, WSL/Linux는 `command -v`로 실제 실행 파일 경로와 버전을 확인한다. 없는 도구를 Windows PATH의 shim으로 대신 실행하거나, 요청 없이 설치하지 않는다.
- 테스트·빌드는 비대화형으로 실행하고 사용자 입력을 기다리는 설치 프로그램, watch 모드, 개발 서버를 테스트 명령으로 실행하지 않는다.
- Windows에서는 PowerShell 7을 명시하고 `~/.config/opencode/scripts/run_bounded_command.ps1`를 사용한다. 기본 제한은 900초이며 빠른 테스트는 300초로 줄인다. 예: `& "$env:USERPROFILE\.config\opencode\scripts\run_bounded_command.ps1" -WorkingDirectory (Get-Location).Path -TimeoutSeconds 300 -Command 'npm test'`.
- WSL/Linux에서는 `~/.config/opencode/scripts/run_bounded_command.sh`로 실행한다. Windows OpenCode에서 WSL 테스트를 요청할 때는 `wsl.exe -d Ubuntu -- bash -lc 'bash ~/.config/opencode/scripts/run_bounded_command.sh --timeout 900 -- python3 -m unittest -v'`처럼 Linux 셸과 Linux 작업 디렉터리를 명시한다.
- WSL에서 `opencode`가 Windows 실행 파일로 연결될 수 있다. `opencode debug paths`와 `file "$(command -v opencode)"`로 확인하고, Windows OpenCode가 Linux 셸을 자동으로 쓴다고 가정하지 않는다. `node`가 없는 WSL에서 Windows `npm` shim을 Linux Node 테스트로 표시하지 않는다.
- macOS 네이티브 OpenCode는 `/bin/zsh`를 사용한다. macOS에서는 `run_bounded_command.sh`가 `timeout` 또는 GNU `gtimeout`을 찾지 못하면 명령 실행 전에 실패한다. 필요한 경우 GNU coreutils의 `gtimeout`을 설치하고, 실제로 확인하지 않은 timeout/프로세스 트리 정리를 성공으로 기록하지 않는다.
- 실행기는 stdin을 닫고 stdout/stderr를 별도 로그에 보존하며 제한 시간 초과 시 자신이 만든 프로세스 트리만 종료한다. 종료 코드와 로그 경로를 확인한다. 시간 초과 뒤 같은 명령을 다시 띄우지 말고 로그와 해당 프로세스 상태를 먼저 조사한다.
- 테스트 중 출력이 없으면 같은 프로세스의 진행 상태를 확인한다. 중복 실행을 만들지 않는다. 시간 초과나 실패는 근거와 함께 기록하고, 원인 변경 없이 같은 테스트를 반복하지 않는다.
